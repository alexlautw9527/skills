以使用者提供的材料為依據，整理能避免誤解的專案詞彙。詞彙表可能適用於整個專案或特定範圍；文件位置、適用範圍與用語規則都由使用者確認，不自行決定。

## Workflow

1. 讀取使用者指定的文件、程式碼、需求或其他材料。只在使用者指定的範圍內整理，不因發現關聯程式碼而擴大分析。
2. 找出反覆出現、容易混淆，或在此專案具有特定含義的詞彙。
3. 在目前範圍內檢查是否已有 glossary，或已有記錄相同資訊的文件。先查閱專案指示文件、文件索引與名稱、內容明確表示用途的文件。
4. 分成兩類呈現結果：
   - 可從材料直接確認的詞彙、定義與既有名稱。
   - 需要使用者決定的名稱、同義詞關係、適用範圍、文件位置或衝突。
5. 向使用者逐項確認需要選擇的內容。若沒有需要確認的內容，仍先確認要更新哪一份既有文件，或要在指定位置建立新文件。
6. 取得確認後，才建立或修改 glossary。若正式名稱改變，先在使用者確認的範圍內更新文件的詞彙與引用，再更新 glossary。修改後說明更新的文件與納入的詞彙。

## 必須先確認的情況

以下情況不可自行推斷或選擇：

- 不確定某個詞是否為正式名稱。
- 同一概念有多個名稱，或不確定兩個相近詞能否互換。
- 要指定慣用名稱，或列出不應使用的名稱。
- 要決定詞彙表適用於整個專案或特定模組。
- 要決定更新既有文件或新增文件，以及檔名與位置。
- 現有文件與使用者提供的材料互相衝突。
- 程式碼只能顯示實作行為，無法直接確認 domain 定義。

使用者尚未確認時，只提供整理結果與待確認事項，不寫入或改動 glossary。

## 詞彙條目

每個詞只記錄已確認且有助於避免誤解的資訊。使用 bullet 呈現條目，不為每個詞建立 Markdown heading，也不為了填滿格式補出規則。

```md
- `<Term>`：<這個詞在目前範圍內代表什麼。>
  - 使用方式：<確認過的使用方式>
  - 不使用：<確認過且容易造成混淆的用法>
```

若材料只足以確認定義，條目只保留名稱與定義。使用方式與不使用僅在已有明確依據時使用。不要為了建立詞彙關係新增「相關詞」欄位；兩個詞的邊界確實會影響使用判斷時，在各自的直接定義中說明。

正式名稱已在確認範圍內完成遷移後，glossary 只保留正式名稱與直接定義，不將已淘汰的名稱保留為對照或變更紀錄。舊名稱仍需支援相容、遷移或外部引用時，才在使用者確認後記錄其關係與移除條件。

## Validation

- 詞彙、定義與命名規則都能追溯到使用者提供的材料或確認結果。
- 文件位置與適用範圍符合使用者確認的選擇。
- 沒有從程式碼推測出的 domain 定義、未確認的同義詞，或自行新增的禁止用詞。
