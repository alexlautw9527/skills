# Learning Flow Addon

將高價值內容的學習放進正在進行的工程工作。讓 AI 處理語法、重複樣板、查閱文件與機械式操作；讓工程師參與會影響設計、驗證、除錯與後續維護的判斷，累積高價值的領域知識，並逐步擴大可獨立處理的問題範圍。

每次互動都必須接回目前工作中的行動或觀察結果。沒有合適機會時，直接繼續原本工作；不要建立獨立的學習階段。

## 先確認是否介入

這個 add-on 只處理已通過 `attention-leverage` 判斷的工程學習機會。使用者直接指定此 skill 時，也先檢查下列條件。

必須同時符合：

- 目前是程式開發、設計判斷、除錯、測試或維護工作。
- 這次理解會改變接下來的實作、驗證、除錯或維護判斷。
- 使用者的回答能立刻由接下來的行動或觀察結果驗證。
- 這次互動不會中斷正在進行的高價值工作。

任一條件不成立時，不出題、不補充教學，直接繼續原本工程工作。

## Scope

執行時：

1. 從目前工作已取得的資訊中，辨識值得讓工程師參與判斷的內容。
2. 判斷目前是否適合插入短互動。
3. 選擇輸入成本最低、能接回目前工作的互動方式。
4. 取得回答後，立即繼續原本工程工作。
5. 同一技術概念或領域知識再次自然出現時，依近期表現調整介入頻率與難度。

不要：

- 為了出題重新探索 repository。
- 接管原本的實作、測試、除錯或規劃流程。
- 提供完整課程、長篇技術教學、學習心得或工作日誌。
- 強迫使用者手寫程式碼。
- 建立永久的學習者資料、能力分數或技能樹。
- 將「使用者批准 AI 已決定的方案」當成工程師參與判斷。

需要保存可供未來工程工作重複使用的發現時，交由 `distill` 判斷。遇到修改成本高、難以回復的設計決策時，可搭配 `reversibility-engineering-pattern` 判斷工程師需要參與到什麼程度。

## 選擇學習內容

先排除語法、API 與可查表資訊。其餘內容只要能帶來工程判斷價值、工程師成長價值或 Domain knowledge 價值其中之一，才考慮介入。

### 工程判斷價值

理解後，工程師是否能更可靠地：

- 決定責任、資料、狀態與模組應放在哪個邊界內。
- 預測一項修改會影響哪些部分。
- 檢查 AI 產生的實作是否符合現有程式碼與限制。
- 選擇能驗證行為的測試或觀察方式。
- 發生異常時，判斷應先檢查資料、狀態、邏輯或呈現的哪一層。
- 辨識系統限制、不變條件與可能失敗的情況。

### 工程師成長價值

理解後，工程師是否能：

- 將概念套用到其他框架、語言或系統。
- 建立對系統運作方式的理解，而非只記住某個 API 的用法。
- 處理原本無法理解的一類問題。
- 補足反覆交由 AI 處理的高判斷價值問題。
- 在目前理解程度上多跨一步，且能透過這次真實工作驗證。

### Domain knowledge 價值

將 Domain knowledge 視為對產品或業務為何必須如此運作的理解。理解後，工程師是否能更準確地理解需求、業務規則與不變條件，並據此判斷實作是否正確。

適合介入的內容包括：

- 使用者實際想完成的工作流程。
- 業務資料各自代表的意義。
- 哪些狀態轉換合法，哪些狀態轉換不應發生。
- 由業務規則產生的不變條件。
- 看似能依一般工程直覺處理，實際上受產品規則限制的例外情況。
- 金流、權限、醫療、會計、法規或其他領域限制所要求的處理方式。
- 技術上看似同一類 bug，實際上代表不同業務問題的情況。

Domain knowledge 只有符合至少一項條件時才值得插入互動：

- 會影響後續需求理解或實作判斷。
- 會反覆出現在目前產品或業務領域。
- 未理解時，容易寫出技術上可執行、卻不符合業務規則的程式碼。
- 構成影響資料或狀態正確性的業務不變條件。
- 能解釋多個看似獨立的需求或例外情況。
- 工程師反覆必須依賴產品經理、文件或 AI 才能理解同類規則。

### 提高介入優先順序的情況

同一類高判斷價值問題、技術能力缺口或 Domain knowledge 反覆由 AI 代為判斷時，提高這類內容的介入優先順序。

### 通常直接處理的內容

- 語法。
- API、參數與可快速查閱的預設值。
- CLI 指令。
- 重複樣板、格式調整與機械式重構。
- 一次性的第三方服務或框架設定細節。
- 可快速重新查到，且不影響工程判斷的資訊。
- 一次性的活動文案、純顯示名稱與只對單一工作項目成立的偶發細節。

## 學習內容判斷流程

```text
遇到可能值得學的內容
        │
        ├─ 只是語法、API 或可快速查到的資訊？
        │      └─ 是 → 由 AI 直接處理
        │
        ▼
理解後是否至少帶來一種價值？
        │
        ├─ 工程判斷更可靠？
        ├─ 可獨立處理的技術問題範圍擴大？
        └─ 更能理解需求、業務規則與不變條件？
        │
        └─ 都沒有 → 不提問
        │
        ▼
目前是否有自然的工作可使用或驗證這項理解？
        │
        └─ 沒有 → 延後或略過
        │
        ▼
以最低輸入成本插入短互動
        │
        ▼
立即回到實際工作
```

## 判斷介入時機

內容值得理解時，仍須確認現在適合提問。優先在工程師的回答能立刻由接下來的行動或觀察驗證時介入。

適合介入的時機：

- 即將進行一項有明確結果的修改，可先預測結果。
- 正在兩個以上各有取捨的方案之間選擇。
- 實際結果與預期不同，需要決定先檢查哪裡。
- 接下來的工作依賴某個機制，未補足目前所需的理解便無法有效判斷。

通常先不介入的情況：

- 使用者正在連續完成機械式工作。
- 前一次互動剛結束，尚未回到實際工作。
- 工作已經完成，只為了補充學習而回頭出題。
- 不同答案不會改變後續觀察、判斷或行動。
- 缺少程式碼、測試、執行結果或規格等證據，無法設計可信題目。

學習互動可在工作中少量出現多次，但每次互動之間必須穿插真實工程工作。

## 選擇互動方式

依目前工作發生的事情，選擇最小互動。

### 預測

接下來能立即看到實際結果時使用。請工程師預測執行時行為、狀態轉換、資料流向、快取行為、畫面呈現，或測試與驗證結果。回答後立即執行原本工作，使用實際結果修正對系統的理解。

### 選擇方案

存在兩個以上合理方案，且選擇會影響實作或驗證結果時使用。選項應呈現不同的責任分配、模組或資料邊界、取捨、實作方向或驗證策略。

不要將命名、語法或機械式選擇包裝成工程決策。難以回復的設計決策可要求一句簡短理由；容易調整的決策通常只需要選擇選項。

### 除錯判斷

預期與實際結果不一致，或已出現 bug、測試失敗時使用。優先請工程師判斷：

- 最可能出問題的是哪一層。
- 下一個最值得取得的觀察結果是什麼。
- 哪個假設最應先排除。
- 哪個驗證方式能以最低成本縮小問題範圍。

不要先完整說明根因，再要求工程師選答案。題目若會直接替工程師完成假設形成過程，先詢問應往哪個方向調查，再根據證據逐步縮小範圍。

### 補充機制說明

只有在不了解某個機制時，工程師無法有效進行預測、選擇方案或除錯判斷，才補充說明。先確認工程師目前理解到哪裡；回答錯誤或選擇「不確定」時，只補足目前工作需要的最小理解。

## 控制輸入成本

優先選擇下列成本較低的互動：

1. 單選。
2. 複選。
3. 選項加上一句簡短理由。
4. 自由輸入一句。
5. 多句文字。

一般情況使用單選或複選。只有難以回復的設計決策、高學習價值的除錯假設，或 AI 無法合理列出答案範圍時，才要求一句文字。

預設提供「不確定」，讓使用者可直接表示目前沒有足夠資訊判斷。AI 無法合理涵蓋答案範圍時，再提供「其他」。

## 設計題目

優先詢問可影響後續工作的工程判斷：

- 接下來預期會發生什麼？
- 哪個方案符合目前限制？
- 先取得哪個觀察結果最能縮小問題範圍？
- 哪個責任邊界較合理？
- 哪種失敗情況最符合目前證據？

不要詢問 API 名稱、選項預設值、函式參數數量或文件原文。

每個選項必須代表不同的系統或業務規則理解、可能失敗原因、責任歸屬、取捨或調查方向。錯誤選項必須來自常見但不正確的理解、目前 repository 容易混淆的資料流、剛被證據排除的假設，或違反限制與不變條件的表面合理方案。

若不同答案不會改變下一步，通常不要提問。互動應形成以下流程：

```text
做出判斷
→ 根據判斷採取行動或取得觀察結果
→ 取得實際回饋
→ 修正對系統的理解
→ 繼續工作
```

## 處理回答

### 回答正確

直接依目前判斷繼續工程工作。需要時，用一句話說明這個判斷會如何影響接下來的實作或驗證。不要追加稱讚、總結或另一題。

### 回答錯誤或選擇不確定

只說明造成誤判的差異，再使用目前已取得的證據驗證正確理解。可使用程式碼、測試、執行時行為、日誌、型別資訊、規格或已取得的 repository 證據。

補足能繼續目前工作的理解後，立即回到原本工作。不要形成「答錯後長篇解釋，再連續出題與回顧」的流程。

## 調整後續互動

同一技術概念或業務規則可在真實工作中再次出現，但不要重複詢問同一題。依工程師的近期表現，後續互動可從辨識與套用，逐步提高到預測與除錯判斷。這些互動不是每次都必經的固定步驟；除錯判斷只在預期與實際結果不一致時使用。

只使用目前工作中自然取得的訊號：剛回答錯誤、剛選擇「不確定」、預測與實際結果不同、已在另一個真實情境正確套用，或同類問題再次完全交給 AI 處理。

回答穩定時降低該技術概念或領域知識的介入頻率；再次出現誤判、不確定或重複依賴 AI 時，提高介入優先順序。不要建立永久的學習者資料。

## 依工作類型調整

### Greenfield

從零建立功能或系統時，優先使用責任邊界、狀態由誰維護、抽象層級取捨、資料模型、業務不變條件、執行時機制與驗證策略作為互動內容。這類工作較常使用「選擇方案」與「預測」。

### Brownfield

修改既有系統時，先建立對目前 repository 實際行為與領域規則的理解。優先使用資料入口與流向、狀態維護位置、相依方向、模組責任、資料在業務上的意義、repository 特有的限制與不變條件，以及工程直覺與程式碼實際行為不同之處。

其他 skill 或實作探索流程已取得這些證據時，直接使用；不要為了產生互動重新探索 repository。這類工作較常使用「預測」與「除錯判斷」。

## Validation

完成目前工作中的責任時，確認：

- 沒有高價值內容時，沒有額外打斷使用者。
- 有學習機會時，互動直接連結正在發生的工程判斷、技術能力成長或可重複使用的 Domain knowledge。
- 優先使用單選或複選，避免不必要的文字輸入。
- 收到回答後，立即回到原本工作並取得實際回饋。
- 沒有為了學習重新執行已完成的 repository 探索。
- 沒有將學習流程擴張成獨立課程、測驗或永久的學習者資料。
