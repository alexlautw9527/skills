# Reversibility Engineering Pattern

適用於無法在開始前列出所有情境，且需求、資料、介面或系統結構可能持續演進的設計工作。

目標是讓合理的新情境、需求調整或既有判斷錯誤發生時，多數設計可以用可接受的成本修正；少數無法避免、修改成本高的決策必須被明確標示與審查。

## 先辨識決策的可回復性

對每項主要決策，依做錯後的修正成本分類。

### 容易調整的決策

決策可以在合理成本內修改、替換或退回原本方案，通常具有下列一項或多項條件：

- 影響範圍限制在單一模組、子系統或尚未公開的介面。
- 新舊方案可以暫時共存，並逐步切換。
- 移除新方案不會破壞既有資料、行為或相依關係。
- 其他部分不需要同時配合修改。

這類決策可以先實作與驗證，再依結果調整。

### 難以調整的決策

決策做錯後需要高成本才能改變，或無法完整恢復，常見原因包括：

- 已公開並被外部使用者、其他服務或大量模組依賴的 API。
- 不相容的資料格式、資料刪除或資料意義變更。
- 需要大規模資料遷移才能替換的資料模型。
- 成為多個模組共同前提的基礎抽象或協定。
- 要求所有使用者、服務或版本在同一時間切換的方案。

記錄這類決策的影響範圍、無法直接復原的原因、替換方案與審查結論。投入較完整的設計、驗證與人類審查。

## Principles

### 保留局部修改的空間

優先選擇可以局部修改、替換或逐步切換的做法。新增一個合理情境時，修改應限於直接負責該情境的規則、模組或資料轉換。

下列徵象表示責任邊界或相依關係需要重新檢查：

- 新增一項行為需要同步修改許多不直接相關的模組。
- 增加一條規則需要重寫既有規則集合。
- 一項局部選擇已滲入公開介面、資料格式或共同基礎層。
- 新方案無法在不破壞既有行為的情況下移除。

需求尚未明確時，先將決策限制在較小範圍。只有已知的變化方向顯示未預留位置會造成高修改成本時，才建立擴充位置；不要只因為假設未來可能變動，就加入尚無使用情境的抽象、策略或外掛機制。

### 減少難以調整的決策

無法避免的高成本決策應保持數量少且位置清楚。

- 能延後決定時，延後到取得足以判斷的資訊之後。
- 能拆成多項局部決策時，避免一次提交為全系統的共同前提。
- 能讓新舊方案共存時，先設計轉換與淘汰路徑。
- 能限制在內部邊界時，不要過早寫入公開 API 或長期資料格式。

### 用 invariant 處理可泛化的情境

不要以列舉方式試圖涵蓋開放式的 edge case。定義所有情境都必須成立的 invariant，讓新增情境可以透過既有條件判斷。

invariant 應描述可驗證的限制，例如：

- 資料狀態保持一致。
- 系統不會產生規格禁止的狀態。
- 操作不會超出授權或允許範圍。
- 無法確認合法性時，系統不會自行產生無法復原的結果。

新增情境若能由 invariant 判斷，就不新增只適用於該情境的例外規則。無法由 invariant 處理時，確認它是否揭露新的責任邊界或必要的產品規則。

### 從結構限制不合法狀態

資料模型、型別、介面、權限或狀態轉換可以直接禁止的錯誤，不應只依靠文字規格要求每個使用方自行避免。

採用結構性限制前，確認它降低的錯誤狀態與規格複雜度，高於它引入的模型或介面複雜度。不要把每一條業務規則都轉換成僵化的結構限制。

## Rules

### 為未知情境指定安全行為

規格尚未涵蓋某個情境時，必須定義實作者可以採取的預設行為，避免自行猜測並產生無法復原的結果。依情境選擇下列其中一種：

- 維持既有行為。
- 拒絕處理並回傳可辨識的結果。
- 保存資料但暫不解讀。
- 交給涵蓋範圍較大的既有規則處理。
- 等取得必要資訊後再決定。

預設行為必須符合 invariant，且不得把不確定性轉換成資料遺失、不可逆寫入或未定義的外部行為。

## Workflow

1. 列出目前要做的主要決策，包括資料、介面、模組邊界、相依關係與遷移方式。
2. 對每項決策說明做錯後的修改範圍、成本與能否讓新舊方案共存。
3. 將高成本或無法完整復原的決策標示為需要額外審查的項目。
4. 針對其餘決策，縮小影響範圍，或提供可替換、可漸進切換的實作路徑。
5. 定義可涵蓋多類情境的 invariant，並用它檢查新增規則與預設行為。
6. 為仍未知的情境指定安全行為。
7. 檢查是否加入未被目前需求支持的擴充機制；移除其帶來的複雜度。
8. 交付設計時，列出剩餘的高成本決策、其原因、影響範圍與需要確認的事項。

## 審查問題

- 這項選擇做錯後，需要修改哪些資料、模組、介面與使用方？
- 修改會不會牽連不直接相關的部分？
- 決策能否先限制在局部範圍？
- 新舊設計能否暫時共存並逐步切換？
- 哪些其他部分會開始依賴這項選擇？
- 哪些 invariant 能涵蓋一整類情境？
- 新增一個合理情境時，會修改多少既有設計？
- 規格未涵蓋的情境會採取什麼安全行為？
- 剩下哪些難以調整的決策？它們是否已獲得所需審查？

## Validation

- 已辨識主要的高成本或無法完整復原決策，並交代其影響範圍。
- 可局部處理的變動沒有被過早擴大為全系統共同前提。
- 已定義能約束多類情境的 invariant，或已說明無法共用的原因。
- 未知情境的預設行為不會造成不可逆結果，且符合既有 invariant。
- 沒有只為假設中的未來需求而加入的擴充機制。
