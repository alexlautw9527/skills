> 執行本 skill 時，預設一併讀取 `make-ai-readable-zh` skill。
將 `AGENTS.md` 作為目前目錄及其子目錄內，供 LLM 修改程式碼時使用的維護知識 SSOT。相關行為或限制改變時，同步更新文件。

## 收錄門檻

只收錄同時符合以下條件的資訊：

- 會影響修改決策。
- 已由負責維護這個範圍的人確認值得納入 SSOT。程式碼、測試、設定與外部文件只作為確認時的依據。
- LLM 容易依一般慣例推論錯誤，或每次都要跨大量檔案重新推導，會耗費大量 token。

省略完整功能規格、目錄與 exported API 已直接呈現的內容、逐步實作說明，以及型別、lint、compiler 或上層指令已保證的規則。

## Workflow

1. 先讀取本目錄及上層目錄的 `AGENTS.md`、`CLAUDE.md` 與其他適用指令，確認以下事項：
   - 這份 `AGENTS.md` 會約束哪些檔案。
   - 上層指令已經規定哪些事項。
   - 本文件是否需要補充更小範圍的限制或不變條件。
2. 閱讀程式碼、測試、設定與相關外部文件，整理以下內容：
   - 模組從哪裡開始執行，以及其他模組可以透過哪些介面使用它。
   - 狀態存在哪裡、由哪些程式碼修改，以及各部分如何互相配合。
   - 模組依賴哪些外部服務，以及這些服務會限制哪些修改。
   - 哪些資訊符合收錄門檻，以及每項資訊可從哪裡查證。
   - 哪些資訊仍需詢問使用者，因為現有資料無法確認。
3. 將候選內容、查證來源與待確認問題交給使用者。由使用者決定哪些內容要收錄，並修正不符合實際情況的描述。
4. 更新 `AGENTS.md`：
   - 將確認要收錄的內容放入下方對應的八個章節。
   - 把文件放在能涵蓋所有受影響檔案的最近一層目錄。只適用於某個子目錄的規則，寫入該子目錄自己的 `AGENTS.md`。
   - 省略沒有內容的章節，並刪除過期、重複、推測而來或工具已能自動保證的內容。
5. 將完成後的文件內容與適用範圍交給使用者確認。使用者確認後，才算完成更新。

## Output

模板說明放在 `instruction` code fence 中。建立正式 `AGENTS.md` 時，以實際內容取代 instruction block；沒有內容的 heading 連同 instruction block 一起刪除。

````md
## Scope

### In Scope

```instruction
說明模組的主要責任與責任邊界：這個模組負責什麼、不負責什麼。省略完整功能列表、從 exported API 就能看出的內容與實作細節。
```

### Out of Scope

```instruction
說明容易被誤認為由本模組負責，實際上由其他模組或外部系統處理的內容。每項說明實際歸屬位置。
```

## Model

```instruction
說明必須跨多個檔案才能建立的整體理解，例如資料流、物件與狀態的關係、生命週期，以及狀態持有者與協調者。省略逐檔案介紹、implementation walkthrough 與從單一函式就能看懂的流程。
```

## Constraints

```instruction
Constraints：記錄限制修改選擇的既有條件，例如 workspace boundary、generated code、state ownership、外部系統或上層模組的依賴限制。每項說明它限制哪些修改，以及可從哪裡查證。省略型別、lint、compiler 或上層指令已保證的規則。
```

## Invariants

```instruction
記錄操作完成後資料必須符合的條件（Invariants）。這些條件用來判斷結果是否正確，以及資料是否還能安全地交給下一個操作使用。

處理過程中可以先改一部分資料，再補齊其他資料。當系統回報操作成功，或其他功能已經可以讀取結果時，所有相關資料必須重新符合規則。

判斷時，把規則改寫成「只要 X 完成，就一定要 Y」或「任何完成的結果都不能出現 Z」。能用這種方式明確判斷對錯，再套用本 skill 的收錄門檻。只用來提醒某個行為容易誤解的內容放入 `Gotchas`。

範例僅用於說明判斷方式：

- 每次一筆交易完成記帳後，資產總額必須等於負債加上權益。各項金額可以改變，這個關係仍須成立。
- 電影院完成出票後，同一場次的同一座位只能屬於一位觀眾。兩個人同時訂位時，只能有一人成功。
- 圖書館完成借書後，同一本實體書只能有一位借閱人。標示為「可借閱」的書不得同時留有尚未歸還的借閱紀錄。
```

## Risks

```instruction
記錄違反一般直覺、容易造成錯誤假設的既有行為，並寫明判斷方式或具體後果。例如 API 無論成功或失敗都回 HTTP 200，必須依 response body 判斷結果。
```

## Rationale

```instruction
記錄看似可以簡化、共用或重構，實際上受限制而刻意維持的設計。每項內容說明目前做法、限制原因，以及替代做法會造成的後果。省略 coding style、沒有後果的偏好與已失效的歷史背景。
```

## Map

```instruction
使用「要修改 X，先看 Y」指出 entry point、決定行為的實作、對應測試與容易漏掉的跨 package 關聯。省略完整目錄樹、所有檔案清單與用 IDE 搜尋即可找到的位置。
```

## Validation

```instruction
說明修改後最低限度要執行的測試、特殊 command、需要 integration test 或 E2E test 的變更，以及 unit test 無法涵蓋的檢查。省略 repository 全域通用的 CI 流程與每個模組相同的 command。
```
````
