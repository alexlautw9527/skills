description: 將產品需求、功能規格或工程工作拆成可驗證的垂直 Slice，並只在必要時列出前置工作。當使用者要求拆功能、排開發順序、建立工作項目、規劃前後端協作，或判斷是否需要前置工作時使用。支援專職前端、專職後端與全端開發情境。
---

依使用者或其他呼叫端可完成的行為拆解工作。垂直 Slice 優先交付可驗證的結果；前置工作只處理無法合理納入行為 Slice 的技術前置條件。

本 skill 只決定行為增量的邊界與順序，不負責將 Slice 繼續拆成 commit 大小的實作 task。

## Inputs

先取得下列資訊。資訊不足時，不要因次要未知資訊阻塞初步切分。

- 需求、行為規格、設計稿或既有工作項目。
- 目標使用者或其他呼叫端，以及預期取得的結果。
- 開發者模式：`frontend`、`backend` 或 `fullstack`。未提供時，依描述推定並明確寫出假設。
- 現有能力、已完成的 Slice、外部相依與不可延後的限制，例如安全性、資料正確性、相容性或法規要求。

將未知資訊分成兩類：

- 不影響 Slice 邊界、順序、責任或完成條件：不必列入輸出，依合理假設繼續切分。
- 可能改變 Slice 邊界、資料正確性、安全性、責任歸屬、先後順序或完成條件：列入 `Unknowns`，明確寫出目前採用的假設，並將受影響的 Slice 標示為 provisional。

交付依建議順序排列的 Slice，說明每個 Slice 的行為、範圍、相依條件、跨職能協作、驗證方式，以及暫不包含的能力。只有確有必要時才列出前置工作。

## Constraints

垂直 Slice 是完成一項可驗證行為所需的最小合理增量。

它可能跨越 UI、API、商業規則、資料儲存或外部服務，也可能只改動其中一層。不要要求每個 Slice 都包含前端、後端、資料庫與測試。

以呼叫端能否取得所宣稱的結果判斷行為是否成立。

- 一般產品通常以使用者完成操作並看見正確結果為準。
- API、CLI、library 或資料服務只要其呼叫端依約定取得正確結果，就能形成完整 Slice，不需要額外建立 UI。
- 「建立資料表」、「新增 endpoint」、「建立元件」、「新增 service」通常是實作活動。只有它本身就是提供給呼叫端使用的能力時，才可直接形成 Slice。

Slice 可以建立在既有能力或先前完成的 Slice 上。相依條件成立後，每個 Slice 都必須新增一個可以直接驗證的結果。

不要要求每個 Slice 在完全沒有其他 Slice 的情況下獨立成立，也不要建立只供後續 Slice 使用、完成後沒有新增可驗證行為的半成品 Slice。

當兩個以上 Slice 共同依賴既有的基礎能力、資料模型、規格理解或實作邊界時，將它列為 `Shared Concerns`，說明受影響的 Slice 與各 Slice 仍各自負責的行為。尚未具備且必須先完成的工作，列為 `Prerequisites`。

不要按照「前端完成」、「後端完成」、「資料庫完成」等技術 layer 切 Slice。不同專長的人可以共同完成同一個行為 Slice。

程式碼目錄依功能或技術分層，屬於目前 repository 的架構決策，不由本 skill 推定。

## Principles

優先保留能在合理的開發與 review 範圍內完成、驗證並取得回饋的最小完整行為增量。

當技術工作可以納入第一個需要它的行為 Slice 時，優先納入該 Slice，不為形式建立獨立的技術前置工作。

## Developer Mode

`Developer Mode` 只限制本次開發者直接負責的實作範圍，不改變 Slice 的行為邊界或整體完成條件。

| 模式 | 本次工作包含 | 跨責任範圍的處理 |
| --- | --- | --- |
| `frontend` | 使用者操作、介面狀態、既有或已確認 API 的串接，以及前端可以完成的驗證。 | 列出所需 API 規格。後端尚未完成時，可依雙方確認的規格使用 mock 開發，但不得因 mock 通過就將整個 Slice 視為已交付。 |
| `backend` | API 或其他服務呼叫端的輸入、商業規則、資料處理、外部整合與回應。 | 列出 client 仍需完成的互動或呈現責任，不將 client 視為已完成。 |
| `fullstack` | 達成行為所需的各層工作。 | 只納入該行為實際需要的層，不為形式加入無關工作。 |

前後端需協作時，列出最低必要的介面規格：

- 呼叫方式。
- 必要輸入。
- 成功回應。
- 可預期失敗。
- 版本、相容性或 rollout 限制。

規格尚未確認，而且會影響實作或驗證時，將確認工作列為阻礙或必要前置工作。

## Workflow

### 1. 描述目標行為

先用一句可驗證的話描述呼叫端完成的行為與結果。

例如：

> 已登入使用者可以建立一筆符合基本規則的預約，並看見建立成功的預約。

不要用資料表、類別、頁面、endpoint 或其他實作物描述目標。

### 2. 先嘗試保留為一個 Slice

判斷整個行為能否在可管理的開發與 review 範圍內完成、驗證並取得有用回饋。

如果可以，先保留為一片。

不要因為實作會碰到多個技術 layer，就自動將它拆開。

### 3. 行為過大時尋找切分邊界

若行為太大，依序嘗試以下邊界。每次切分後，都必須重新檢查每一片是否產生新增且可驗證的結果。

- 工作流程邊界：
  - 尋找可以提前形成完整結果的流程階段。
  - 只有某個階段本身能讓呼叫端完成一項有意義的行為時，才能獨立形成 Slice。
  - 不要僅因操作流程包含多個步驟，就逐步拆成 Slice。
  - 例如，結帳流程不直接依選擇地址、選擇付款方式與送出訂單切開；可先讓使用者以預設地址和單一付款方式完成訂購，再依序支援改用既有地址與新增地址。

- 情境：
  - 先完成基本成功流程，再加入其他能獨立驗證的情境，例如沒有結果、可恢復失敗、部分成功或特殊輸入。
  - 若某種失敗處理缺少時會造成錯誤資料、安全問題或誤導使用者，就不能延後到另一片。

- 操作者角色：
  - 不同角色具有不同能力時，可以依角色切分。
  - 例如，先讓一般使用者完成基本操作，再提供管理者的額外管理能力。
  - 不要只因畫面或權限判斷程式位於不同地方就切開。

- 資料範圍：
  - 先支援較窄但完整的資料範圍，再擴充合法範圍。
  - 例如一筆到多筆、一種類型到多種類型、小型資料集到大型資料集、單一資料來源到多來源。

- 商業規則：
  - 先支援較小但正確的規則集合，再加入可以安全延後的能力。
  - 例如，先實作基本資格，再加入折扣；先支援一般權限，再加入特殊例外；先完成標準流程，再加入進階設定。
  - 移除某個規則會造成錯誤資料、安全問題、違反契約或誤導呼叫端時，必須保留在同一片。

- 能力廣度：
  - 優先尋找先提供較窄但完整的能力，再逐步擴大適用範圍的切法。
  - 不要先建立完整 framework，再把真正可用的能力放到最後。
  - 例如，CSV 匯入可先支援格式正確且沒有重複資料的小型檔案，再加入不合法資料的錯誤回報、與既有資料重複的處理，以及大型檔案的非同步處理。

### 4. 判斷是否停止切分

當 Slice 已能在合理的開發與 review 範圍內完成，而且繼續拆分只會產生實作步驟、技術 layer 或沒有新增回饋價值的中間狀態時，停止切分。

判斷方式：

- 如果繼續切分後，兩邊都能描述成新的可觀察結果，可以繼續評估是否值得切。
- 如果其中一邊只能描述成「建立 X」、「修改 Y」、「串接 Z」、「準備共用元件」等實作活動，通常不要再切。

Slice 的目標不是切到最小工作量，而是切到足以降低交付風險，同時仍保留完整行為。

### 5. 指定完成條件與驗證方式

每一片都必須指定驗證方式。

驗證必須直接證明呼叫端取得該 Slice 所宣稱的新結果。

可使用：

- 實際 UI 操作。
- API request / response。
- CLI command。
- integration test。
- acceptance test。
- 可觀察的資料或外部系統結果。

單獨證明某個 class、資料表或內部函式存在，通常不足以證明行為 Slice 已完成。

### 6. 排序

依下列因素安排 Slice 順序：

- 使用價值。
- 是否能提早取得產品回饋。
- 是否能提早驗證高風險假設。
- 技術或外部相依。
- 安全性、資料正確性與相容性限制。

優先取得高價值或高風險假設的實際回饋。

相依關係可以限制可行順序，但不要為了預先建立通用能力而製造原本不存在的前置工作。

若最窄的第一個行為 Slice 可以同時建立必要底層能力，優先將技術工作包含在該 Slice 內。

## Prerequisites

發現技術相依時，不立即建立 Prerequisite。

先嘗試將最小必要的技術變更納入第一個需要它的行為 Slice。只有工作無法合理形成呼叫端可驗證的行為，或必須先獨立完成才能避免不可接受的交付風險時，才建立前置工作。

常見情況包括：

- runtime 或 framework 升級。
- 必須先獨立 rollout 的資料遷移。
- 基礎設施設定。
- 安全修補。
- 多個後續 Slice 都必須依賴的共用可觀測性能力。
- 用來消除重大技術不確定性的限時 spike。

例如，單純為某個新行為新增資料欄位，通常應納入第一個使用該欄位的 Slice，不應自動成為 Prerequisite。

每個前置工作都必須包含：

- 原因：為何不能安全納入第一個需要它的行為 Slice。
- 受益 Slice：哪些後續行為需要它。
- 完成條件：做到什麼程度即停止。
- 後續行為：完成後最先啟動或解除阻礙的 Slice。

不要用假使用者故事包裝技術前置工作，也不要讓前置工作擴張成沒有明確成果的平台整理、重構或通用 framework 建設。

## Validation

輸出前逐項檢查：

* 每個 Slice 都以呼叫端的行為與新增結果描述，不以技術元件或實作活動命名。
* 每個 Slice 在列明的相依條件成立後，都能直接驗證其新增結果。
* Slice 可以建立在先前 Slice 上，但沒有只供後續 Slice 使用、完成後沒有新增可驗證行為的半成品。
* 繼續拆分若只會得到技術 layer、實作步驟或內部元件，已停止切分。
* 每個 Slice 都區分目前包含的範圍與可以安全延後的能力。
* `Shared Concerns` 只列已存在且由兩個以上 Slice 共同依賴的前提，沒有包裝成獨立的行為 Slice 或前置工作。
* `Developer Mode` 沒有改變 Slice 的整體行為邊界與完成條件。
* 專職開發者的本次工作沒有暗中包含其他職能的實作責任。
* 使用 mock 驗證專職開發者工作時，沒有把 mock 通過誤寫成跨系統 Slice 已完成。
* 每個 Slice 都保留所宣稱行為必要的資料正確性、安全性、相容性與失敗處理。
* 技術相依已先嘗試納入第一個需要它的行為 Slice，而不是自動建立 Prerequisite。
* 尚未具備且必須先完成的共同前提已列為 `Prerequisites`，沒有誤列為 `Shared Concerns`。
* 每個 Prerequisite 都有明確原因、受益 Slice、停止條件與解除的後續行為。
* 排序沒有為了預先建立 abstraction、framework 或平台能力而製造不必要的前置工作。
* 輸出沒有把技術分層、程式碼目錄、特定架構或特定 framework 當成普遍規則。
* 本 skill 沒有繼續把 Slice 拆成 commit 大小的實作 task。
