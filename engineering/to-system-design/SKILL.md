# system design

將行為規格轉成實作前必須決定的責任邊界、資料處理方式與跨系統協作。設計文件記錄結論與理由，不以固定模板取代設計。

## Inputs

先取得目前可用的材料：

- 使用者需求、sbe、驗收條件、ui design 或既有產品行為。
- 相關程式碼、專案指示文件、架構文件、API 規格、資料結構定義與測試。
- 平台、安全性、資料正確性、相容性、效能、容量與維運限制。
- 使用者指定的 Scope，以及不能改變的責任邊界。

先讀取適用範圍的 `AGENTS.md`、`CLAUDE.md`、README 與 `GLOSSARY.md`。從目前環境確認程式碼位置、介面與資料流；不要把需求中的技術建議當成既有實作。

資料不足時依影響處理：

- 不改變可觀察行為、資料正確性、責任歸屬、主要介面或設計選擇的未知資訊，可以寫明前提後繼續。
- 會使設計採用不同方案的未知資訊，列入 `Questions`，說明受影響的 Decision 與暫定前提。
- 缺少答案就無法判斷安全性、資料正確性、相容性或公開介面時，停止鎖定受影響的 Decision，交由需求或技術負責人決定。

## Constraints

- 只設計本次行為需要的範圍。不要因為功能可能涉及資料儲存、背景工作或外部服務，就預設加入 database、cache、queue、event bus、microservice 或基礎設施。
- 優先沿用仍符合本次限制的既有模式與介面。既有抽象層不符合行為或限制時，說明不沿用的理由。
- 公開介面、跨模組協作、持久化資料、狀態由誰管理與安全邊界必須明確設計。私有函式、檔案拆分、命名與局部演算法留給實作決定。
- 每個結論都要對應行為、限制、失敗結果或修改成本。不要以「可擴充」、「高效能」或「可維護」取代這些依據。
- 沒有需求或近期證據時，不建立通用框架、預留服務、事件機制或設定項。將刻意延後的選擇記錄在 `Decisions`，並標示重新評估條件。

## Workflow

### 1. 判斷綠地或棕地，整理 Scope 與 Map

先用 `Scope` 確認本次要完成的可觀察行為、`In Scope`、`Out of Scope` 與會改變設計的限制。只檢查實際碰到的設計面向，例如用戶端、應用程式狀態、本機持久化、API、持久化資料、外部服務、背景工作或端到端流程。

- 綠地：建立尚未存在的新能力。根據需求、平台限制與已知外部系統設計初始結構。只有外部系統、平台限制或初始整合邊界會影響設計時，才建立 `Map`。
- 棕地：修改既有能力。必須先建立 `Map`，避免誤改既有責任、資料流或相依關係。

建立 `Map` 時，從與行為最接近的入口開始，找出目前存在且會影響設計選擇的：

- 入口、資料流與對呼叫端可見的結果。
- 哪個部分管理狀態、資料最後以誰為準，以及持久化位置。
- 已有的 API、事件、資料結構定義、相容性限制與外部相依。
- 一至三個資料流相似、可以沿用的做法及其適用條件。

`Map` 只記錄既有事實。不要列出預計新增的程式碼，也不要盤點無關的系統部分。

### 2. 走讀主要流程，找出設計決策

從觸發事件走到呼叫端可觀察的結果。每個主要流程都要說明：

1. 呼叫端如何開始操作。
2. 哪些狀態被讀取、改變或持久化。
3. 哪些邊界被跨越，以及傳遞的資料或控制訊息。
4. 哪些操作同步完成，哪些交給其他系統或背景處理。
5. 呼叫端如何得知成功、失敗或結果尚未確定。

在流程中標記狀態改變、非同步交接、併發、外部相依、持久化、信任邊界與平台中斷點。只有符合下列條件時，才建立正式設計決策：

- 有兩個以上可行方案，選擇會改變系統行為或結構。
- 失敗後留下的狀態、資料或操作由誰負責尚未定義。
- 跨系統介面、信任邊界、相容性要求或前提不清楚。
- 選錯後需要遷移資料、修改多個呼叫端，或重新安排系統責任。

優先處理修改成本高的選擇，例如狀態由誰管理、本機持久化、同步方式、公開或跨模組介面、持久化資料結構、事件規格、資料維護責任、一致性模型、授權邊界與共用基礎設施。

修改成本高或難以撤回的選擇，依 `reversibility-engineering-pattern` 檢查：做錯後會影響哪些資料、模組、介面與使用方，新舊方案能否暫時共存，以及需要什麼替換或審查安排。

### 3. 完成決策與設計方案

每個有實際取捨的設計決策都使用下列結構。只有一個合理方案時，直接說明依據，不要為了湊數建立替代方案。

```markdown
### <Decision 名稱>

#### Context

- <會影響選擇的行為、限制或風險>

#### Options

- <實際可行方案>

#### Decision

<採用或延後的方案>

#### Consequences

- <得到的能力>
- <接受的限制、成本或後續責任>
- <若難以撤回：影響範圍、新舊方案能否共存，以及替換或審查安排>
```

先排除違反明確需求的方案。比較其餘方案時，檢查成立條件、失敗結果、實作與維運成本，以及未來修改時需要動到的範圍。不要用加權分數取代理由。

能限制在內部或局部範圍的選擇，不要過早寫入公開 API、長期資料格式或共用基礎層。無法避免的難以撤回決策，必須記錄影響範圍、不能直接復原的原因與替換方式，並標示需要的審查。

再將已選定的決策組成 `Proposed Design`，讓實作者看得出：

- 主要部分各自處理什麼責任。
- 狀態位於哪裡、由誰維護，以及何時失效或恢復。
- 資料如何跨越用戶端、服務、資料儲存與外部相依。
- 介面如何表示成功、失敗與結果不明。
- 失敗如何傳給呼叫端、重試或隔離。

公開 API、跨團隊協定、持久化資料遷移、新的共用基礎設施或安全邊界，可以標示為 `ADR candidate`，但不在本 skill 內建立 ADR。

### 4. 只在圖能回答問題時加入圖表

先查目前專案的圖表慣例。已有 PlantUML、Structurizr DSL、C4-PlantUML、Graphviz 或其他 diagram-as-code 格式時，沿用既有格式。同一份設計不要為了單一圖混用不同語法。

沒有既有慣例時，使用 Mermaid。每張圖只回答一個問題：

| 想回答的問題 | 使用圖表 |
| --- | --- |
| 主要部分、責任邊界、相依或資料流 | `flowchart` |
| 呼叫順序、非同步交接、重試或失敗傳遞 | `sequenceDiagram` |
| 合法狀態、轉換、重試與終止狀態 | `stateDiagram-v2` |
| 關聯式資料的關係與 cardinality | `erDiagram` |

- `flowchart` 的節點代表有明確責任的系統部分。關係方向不清楚時，在箭頭標示呼叫、讀寫或事件語意。主要節點超過約 15 個時，分成總覽與局部圖。
- `sequenceDiagram` 在順序影響資料正確性時使用。只用 `alt`、`opt`、`loop` 或 `par` 表達會改變設計的分支。
- `stateDiagram-v2` 只表示呼叫端或系統能觀察到的狀態。確認事件由誰觸發、操作中斷後停在哪裡、重試從何處開始，以及是否有無法離開的狀態。
- `erDiagram` 只在資料關係、持有者或 cardinality 會改變行為、查詢或一致性時使用。欄位、索引、限制與遷移放在文字或資料結構定義中。

大型系統需要從外部系統逐層看進來，或現有文件已採用 C4 時，才使用 C4。圖表完成後，確認節點與關係都存在於 `Proposed Design`，且流程方向與 `Key Flows` 一致。

### 5. 驗證主要流程、失敗處理與恢復方式

重新走讀每個行為規格，只檢查會改變本次設計正確性的失敗情境：

- 同一操作重複執行、逾時後結果不明，或只有部分操作完成。
- 多個操作方同時操作，或舊資料覆蓋新資料。
- 外部相依失敗、延遲過久或回傳順序改變。
- 依平台而定的重新整理、路由切換、程序終止、網路中斷或背景執行中斷。

每個相關情境都要寫出事件後可觀察到的狀態、是否能重試，以及由誰負責恢復處理。答案不明確時，回到 `Decisions` 修正設計，不要只留下風險清單。

sbe 使用 Given / When / Then 時，對應驗證方式如下：

- Given：初始狀態、授權條件與外部前提由哪個部分表示或驗證。
- When：事件會經過哪些主要部分與介面。
- Then：哪個狀態或輸出使呼叫端能驗證結果。

### 6. 交接至後續工作

需要確認實作位置、跨 repository 範圍、既有模式或需求追溯關係時，使用 `to-plan`；它已包含 slice 切分。行為、設計邊界與驗證方式已足夠明確，且不需要完整計畫時，直接使用 `to-slices`。完成其中一項後，再由 `to-tasks` 依已確認的 slice 與設計結果拆出 task。

`Handoff` 帶入已決定的介面、狀態由誰管理、資料與相容性限制、必要前置工作、`ADR candidate` 與仍會影響 Scope 的 Questions。後續工作不得重新決定這些設計。

## Output

依實際設計交付 Markdown 文件。`Scope`、`Proposed Design` 與 `Key Flows` 是預設結構。棕地 feature 與需要說明既有外部邊界的綠地 feature 必須加入 `Map`；`Decisions`、`Failure Handling and Recovery` 與 `Questions` 只有在需要回答對應問題時才加入。

```markdown
# system design: <功能名稱>

## Scope

### In Scope

### Out of Scope

## Map

<棕地 feature，或需說明既有外部邊界的綠地 feature 才保留本節。>

## Proposed Design

## Decisions

## Key Flows

## Failure Handling and Recovery

## Questions

## Handoff
```

- `Scope` 說明要完成的行為、刻意不處理的範圍與影響設計的限制。
- `Map` 指出既有入口、實作位置、資料流、資料由誰維護、系統邊界與可沿用模式。
- `Proposed Design` 說明系統如何透過責任分工、資料流與主要流程達成 Scope。只有某個設計問題會影響實作、驗證或 review，且無法由其他段落清楚說明時，才新增子標題。子標題直接描述該問題、責任或設計決策，不預設技術分類。
- `Decisions` 記錄有方案取捨或刻意延後的選擇與後果，不重述 Proposed Design。
- `Key Flows` 說明主要行為如何從開始走到可觀察結果。
- `Failure Handling and Recovery` 說明會改變資料正確性、呼叫端結果或恢復責任的失敗情境。
- `Questions` 只保留尚未確認且會改變設計或後續拆分的事項；沒有此類問題時寫「無」。
- `Handoff` 指明下一步使用 `to-plan` 或 `to-slices` 的理由與需要帶入的設計結果。

需要讀者回查依據時，直接連結或引用 Inputs 中的具體段落，例如 sbe 的 Rule、API 規格、既有架構文件或程式碼位置。文件本身仍要寫出設計結論與理由，不用複製來源內容。

## Stop Conditions

符合下列條件後停止擴大設計：

- 所有必要行為都能從開始走到可觀察結果。
- 會影響正確性的失敗、中斷與重複操作都有明確結果。
- 狀態由誰管理、主要責任邊界與跨系統介面已清楚。
- 已知的量化與平台限制有可說明的滿足方式。
- 修改成本高的 Decisions、前提與取捨已記錄。
- 餘下選擇可以安全留給實作階段決定，或已在 `Decisions` 標示延後的條件。

不要繼續為沒有需求證據的未來情境增加架構。

## Validation

交付前確認：

- `Scope`、`Map`、`Proposed Design`、`Key Flows`、`Failure Handling and Recovery`、`Questions` 與 `Handoff` 各自回答不同問題，沒有重複內容。
- 有 `Map` 時，每項說明都可由目前系統或引用的 Inputs 證實。
- 每項設計決策都說明 Context、可行 Options、採用或延後的選擇與 Consequences。
- `Proposed Design`、圖表與 `Key Flows` 對狀態、責任與流程的描述一致。
- 所有會影響正確性的失敗情境都有可觀察結果，並清楚說明恢復處理由誰負責。
- 文件沒有預先指定可安全留給實作階段決定的內部細節。
- 後續的 `to-plan` 或 `to-slices` 能不重新設計架構，就開始切分可驗證的工作。
