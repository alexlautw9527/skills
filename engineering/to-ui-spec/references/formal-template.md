## 規則

### 類型判定

先看這條要核對的可觀察結果，再選類型。條件與觸發時機寫進 `說明：`，不拿來選類型。

判定順序：

1. 結果是另開畫面、頁面跳轉、畫面切換，或使用者操作開關／下拉／按鈕進出：`流程`。點擊後因條件開啟彈窗也歸此類，條件仍寫在說明。
2. 結果是畫面上既有元素因狀態或條件出現、隱藏、消失（不是使用者主動打開那個元素）：`顯示`。包含條件成立才出現的標籤、Alert、卡片、篩選後列出來的列。
3. 結果是資料怎麼算、自動修正、可否送出、同畫面欄位錯誤、控制項停用：`規則`。
4. 結果是元素在版面上的固定位置、欄位歸屬、清單排序位置、控制項種類：`結構`。`結構` 管元素長期存在於版面的哪裡；`顯示` 管它什麼時候看得到。
5. 結果是固定文案本身：`內容`。
6. 結果是已存在元素的顏色、對齊、字級、狀態外觀：`樣式`。

同一項同時符合多種類型時：

- 同一項同時符合 `規則` 與 `流程` 時，若可觀察結果是彈窗開關、頁面跳轉或畫面切換，標為 `流程`，並將觸發條件寫入說明。
- 同一項同時符合 `規則` 與 `顯示` 時，若可觀察結果是元素出現或隱藏，標為 `顯示`，並將條件寫入說明。只有「匹配哪些資料」可以獨立核對時，才另建一項 `規則`。例如篩選條件決定哪些資料符合條件，而結果列如何展開母層則屬於 `顯示`。
- 同一項同時符合 `顯示` 與 `樣式` 時，元素持續存在而外觀改變就標為 `樣式`；元素是否出現則標為 `顯示`。
- 阻擋操作：開了新畫面標 `流程`；同畫面錯誤、停用、無法送出標 `規則`。

### 系統回饋

系統回饋是畫面因操作或狀態變化而出現的回應，包括彈窗、Alert、輸入欄驗證錯誤、阻擋訊息、提示訊息、toast 與 tooltip。條目提到系統回饋時，下列三件事都要能對上：

- `說明：` 寫明回饋的具體形式與出現位置，並以來源資料中的畫面狀態與鄰近文字判斷。
- `文案：` 逐字寫出回饋的實際文字；含動態數值時照 Figma 原文寫，並在 `說明：` 註明數值如何計算。文案可寫在本條；也可省略本條 `文案：`，改以 `關聯：` 指向已寫原文的那條。
- `驗證：` 回饋若是另開的畫面，在對應步驟附上該 Figma node。這條要核對的畫面若已列於本項 `來源：`，不必在驗證重複相同 URL。

任一項無法從來源資料判斷時，依 source-rules.md 建立 Question，不得用籠統描述帶過。

### Section

- 每個 Section 根的 `來源：` 連結文字必須是該 node 的 `titlePath` 或 `name`。無法對應到特定 node 的泛稱標籤視同未命名，scaffold 與整理都不可過關。
- 在 `## Reading Guide` 之後維護 **Section 索引表**（Section 標題 ↔ slug）。slug 為英文 kebab-case、語意短名、檔內唯一；新增 Section 時指定新 slug，**不得**因插入而改舊 slug。
- Section 內 UI 驗收項依 `類型` 分組排列，固定順序：`規則` → `顯示` → `結構` → `流程` → `內容` → `樣式`；同類型內依來源資料出現順序。
- UI 驗收項在 Section **內**依類型排序後從 `01` 編號，格式為 `UI-<section-slug>-NN`。新增 UI 項只影響同 Section 後續編號，不影響其他 Section。
