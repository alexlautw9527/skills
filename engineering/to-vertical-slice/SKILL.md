依使用者或其他呼叫端可完成的行為拆解工作。垂直切片優先交付可驗證的結果；水平工作只處理不能合理包成行為的技術前置條件。

## Inputs

先取得下列資訊。缺少但不影響初步切分時，列為假設與待確認事項。

- 需求、行為規格、設計稿或既有工作項目。
- 目標使用者或呼叫端，以及預期結果。
- 開發者模式：`frontend`、`backend` 或 `fullstack`。未提供時，依描述推定並寫出假設。
- 現有能力、外部相依與不可延後的限制，例如安全性、資料正確性或法規要求。

交付依優先順序排列的切片，說明每一片的行為、範圍、相依條件、驗證方式，以及暫不包含的能力。只有確有必要時才列出水平工作。

## Rules

垂直切片是完成一項可獨立驗證行為所需的最小範圍。它可能跨越 UI、API、商業規則、資料儲存或外部服務，也可能只改動其中一層。不要要求每個切片都包含前端、後端、資料庫與測試。

以呼叫端能否取得完整結果判斷是否完成。

- 一般產品的結果通常是使用者完成操作並看見正確結果。
- API、CLI 或資料服務的呼叫端依約定取得正確結果，即可形成完整切片，不需要另做 UI。
- 「建立資料表」、「新增 endpoint」或「完成元件」通常是實作活動；除非它本身就是交付給呼叫端的能力。

不要切成「前端完成」、「後端完成」或「資料庫完成」等無法單獨帶來結果的階段。前端與後端可由不同專長的人負責，但仍應共同服務同一個行為切片。

程式碼目錄是否依功能或技術分層，屬於目前 repository 的架構決策，不由本 skill 推定。

## Workflow

1. 用一句可驗證的話描述行為與結果，例如「已登入使用者可以建立一筆符合基本規則的預約」。不要以資料表、類別、頁面或 endpoint 描述目標。
2. 判斷這個行為能否在一次可管理的交付中完成、驗證與取得回饋。若可以，先保留為一片。
3. 若行為太大，依序嘗試以下邊界；每次切分後都檢查行為能否獨立驗證：
   - 工作流程的一步，例如先選項目，再確認送出。
   - 情境，例如基本成功流程、沒有結果或可恢復的失敗。
   - 操作者角色，例如一般使用者與管理者。
   - 資料範圍，例如一筆與多筆、一種類型與多種類型。
   - 商業規則，例如基本資格，再加入折扣、權限或例外條件。
4. 先交付最小可用範圍，再擴充能力。若移除某個規則後會產生錯誤資料、安全問題或誤導使用者，就將該規則與行為保留在同一片。
5. 為每一片指定完成條件與驗證方式。驗證必須直接證明呼叫端取得所宣稱的結果。
6. 依價值、風險、回饋與相依關係排序。優先安排被其他片依賴的最小行為或必要前置工作。

## Scope

行為邊界不因職能而改變；本次可直接實作的範圍與需協作的部分會改變。

| 模式 | 本次工作包含 | 跨責任範圍的處理 |
| --- | --- | --- |
| `frontend`  | 使用者操作、介面狀態、既有或已約定 API 的串接，以及前端可驗證結果。 | 列出所需 API 規格。後端尚未可用時，依雙方確認的規格使用 mock，不臆測 API。 |
| `backend`   | API 或其他服務呼叫端的輸入、規則、資料處理與回應。                  | 列出 client 需要完成的互動或呈現方式，不將 client 視為已完成。             |
| `fullstack` | 達成行為所需的各層工作。                                            | 只納入行為實際需要的層，不為形式加入不相關的層。                           |

前後端需協作時，列出 API 規格的最低必要內容：呼叫方式、輸入、成功回應、可預期失敗，以及版本或相容性限制。規格未確認時，將確認工作列為阻礙或先行工作。

## Prerequisites

只有工作無法合理形成呼叫端可驗證的行為時，才建立水平工作。常見情況包括 runtime 或 framework 升級、資料遷移、基礎設施設定、安全修補、共用可觀測性能力，或研究不確定方案的 spike。

每個水平工作都必須包含：

- 原因：為何不能安全地切成可交付的行為。
- 受益切片：哪些後續行為需要它。
- 完成條件：做到什麼程度即停止。
- 後續行為：完成後最先啟動或解除阻礙的垂直切片。

不要用假使用者故事包裝這類工作，也不要讓它擴張成沒有明確成果的平台整理。

## Output

```markdown
## Goal

<呼叫端> 要完成的行為與結果。

## 假設與待確認事項

- <只列影響切分、順序或責任的未知資訊>

## 開發者模式

`frontend` | `backend` | `fullstack`

## 切片 1：<短名稱>

- 可觀察行為：<誰做什麼後，取得什麼結果>
- 包含：<達成此行為不可少的範圍>
- 暫不包含：<可安全延後的能力>
- 相依與協作：<既有能力、API 規格或其他團隊工作；沒有則寫「無」>
- 驗證：<如何證明呼叫端已取得結果>

## 切片 2：<短名稱>

...

## Prerequisites

若無必要，寫「無」。若有，每項依序列出原因、受益切片、完成條件與後續行為。
```

## Validation

- 每個垂直切片都以行為與結果命名，且不完成其他切片也能驗證。
- 每片都區分本次範圍與可安全延後的能力。
- 專職開發者的交付沒有暗中包含其他職能的實作責任。
- 切片保留了所宣稱行為需要的資料正確性、安全性與失敗處理。
- 水平工作有明確邊界，並且連回後續垂直切片。
- 輸出沒有把技術分層、程式碼目錄或特定框架當成普遍規則。
