註解只補充程式碼無法直接表達，且會影響維護判斷的資訊。

## 適用情境

- 新增或修改註解。
- 審查註解是否重複、失真或缺少必要背景。
- 重構或修正程式後，確認註解仍符合目前行為。

開始前讀取相關程式碼、測試、文件、外部規格與 repository 指示。資料不足時保留未知事項，不把推測寫成事實。

## Workflow

1. 找出日後修改時可能導致錯誤判斷的資訊。
2. 先確認能否透過命名、型別、函式拆分、資料結構或測試表達。
3. 只有仍需補充時，才在決策點附近撰寫註解。
4. 修改行為後，同步修改或刪除相關註解。
5. 重新檢查註解、程式碼、型別、測試與規格是否一致。

## 應保留的資訊

- 目前做法的原因，以及替代做法會造成的結果。
- 公開 API、模組邊界、跨檔案關係與外部協定。
- 必須持續成立的順序、狀態、資料限制或其他不變條件。
- 防禦性檢查所防止的錯誤輸入、外部資料或環境問題。
- 暫時 workaround 的原因、影響，以及可移除它的條件。
- 看似異常、但為了維持行為或相容性而刻意保留的例外。

註解使用現在式描述可由程式碼、測試或規格驗證的事實。外部規格是依據時，附上可查閱的連結或文件識別資訊。

## 應避免的內容

- 逐行翻譯程式碼正在做什麼。
- 重述函式名稱、型別、測試或明顯的控制流程。
- 沒有原因、限制或可驗證依據的通用提醒。
- 未經證實的業務規則、外部規格或歷史原因。
- 集中放在檔案開頭，且必須與程式碼來回對照才能理解的註解。

## 暫時性註記

`TODO` 或 `FIXME` 必須包含：

- 目前無法處理的原因。
- 造成的影響或風險。
- 可以移除註記或改用完整做法的具體條件。

缺少這些資訊時，改建立可追蹤的工作項目，或直接處理問題。

## 失敗處理

- 註解只描述 what：刪除，或改寫成原因、契約、邊界或不變條件。
- 註解與程式碼不一致：依目前行為、測試與規格修改或刪除註解。
- 原因尚未確認：停止撰寫該註解，先補充可驗證來源。
- 註解範圍過大：拆到各自的決策點，或改由模組文件保存。
- 行為已改變但註解未更新：將註解納入同一項程式碼變更重新審查。

## Output

依使用者要求交付程式碼變更或審查結果。審查結果至少說明：

- 註解補充了哪些程式碼無法直接表達的資訊。
- 註解是否符合目前行為與來源。
- 哪些位置應修改、刪除或補充，以及原因。

若不需要註解，說明現有的命名、型別、測試或程式結構已足以表達相關資訊。

## Validation

- 能在程式碼中找到註解描述的決策點、邊界或不變條件。
- 註解沒有重複程式碼、型別或測試已表達的內容。
- 原因、條件、責任歸屬與影響範圍都有可驗證依據。
- 變更後沒有留下過期、矛盾或缺少移除條件的註解。
- 依 repository 的既有方式執行相關測試、靜態檢查或文件驗證；未執行時說明原因。

## Stop Conditions

遇到以下情況時停止增加註解：

- 程式碼、型別、測試與既有文件已足以支持維護判斷。
- 新內容只會重複命名、控制流程或測試意義。
- 原因、限制或外部規格尚未取得可驗證來源。
- 背景資訊已超出局部程式碼的範圍，應改由模組文件或規格文件保存。
