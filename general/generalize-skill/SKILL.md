---
name: generalize-skill
description: 泛化 skill 中的專案特定假設。建立、修改或審查 skill，且內容可能綁定特定專案、框架、目錄結構、領域名稱、API 或未證實的未來需求時使用。
---

保留處理同類任務時都需要的規則。專案名稱、目錄結構與團隊做法等可變資訊，改由執行者從目前環境查證。

## 1. 確認適用範圍

寫出這個 skill 要處理的任務類型，並確認：

- 執行時需要哪些輸入。
- 完成後要交付哪些結果。
- 執行者依據哪些規則做決定，以及要按照什麼順序工作。
- 任務完成後，哪些條件一定要成立。
- 發生錯誤或資料不足時，應如何處理。

若 skill 明確服務特定產品、工具或組織，將不可缺少的專有資訊視為適用範圍，並寫入 `description`。

完成條件：每項內容都能判定為同類任務普遍需要的規則、skill 本身的適用範圍，或目前專案的做法。

## 2. 找出專案特定假設

逐項檢查檔名、目錄、框架、元件、領域實體、API、指令與團隊慣例。對每一項內容回答：

1. 換成另一個合理的專案、框架或目錄結構後，這項規則是否仍然成立？
2. 能否改用角色、關係或類別表達，使規則脫離目前名稱？
3. 這項資訊應由 skill 保存，還是應在執行時從專案指示文件、README、規格、程式碼或使用者輸入取得？

完成條件：每項專案特定假設都已標記為刪除、改寫成通用規則、執行時查證，或保留為 skill 的適用範圍。

## 3. 泛化規則

依照前一步的分類修改內容：

- 將可變名稱改成描述用途的角色、類別或 placeholder，例如 `<feature-dir>`、`<behavior-spec>`、`<existing-module>`。每個 placeholder 都要說明用途、資料來源，以及何時已取得足夠資料。
- 將可從目前環境確認的資訊改成執行時查證，並指出應查閱哪一類來源。
- 保留會影響執行者決策的通用規則、工作順序、完成條件與失敗處理方式。
- 保留完成任務不可缺少的產品、工具或組織限制，並在 `description` 限定適用範圍。
- 只抽出已知會重複出現的決策方式。依 YAGNI 原則，省略目前沒有需求的分支、設定與擴充點。

完成條件：移除目前專案的名稱與技術棧後，所有通用規則仍能直接執行；剩餘的專有資訊都屬於 `description` 已說明的適用範圍。

## 4. 檢查範例

若 skill 沒有範例，略過這一步。需要範例時，優先使用 placeholder；具體情境應標示為「僅供示範」。

- 後續規則使用與範例無關的名稱與條件。
- 有多個範例時，使用不同的專案情境。
- 範例只展示既有規則；限制與預設值直接寫入規則。

完成條件：移除任何範例後，規則仍然完整，而且其他合理的專案可以套用同一規則。

## 5. 驗證泛化結果

1. 重新檢查第 2 步列出的每項專案特定假設，確認處理結果已反映在 skill 中。
2. 選擇三個結構不同、任務類型相同的假想專案，確認流程與完成條件都能直接使用。
3. 刪除為了通過假想案例而新增、目前沒有實際需求的分支。

完成條件：所有專案特定假設都有明確處理結果；三個假想專案都能使用同一套流程；新增內容都對應目前需求。

## 交付內容

- 修改 skill 時，交付泛化後的內容，並列出仍保留的專案特定假設及保留原因。
- 只審查 skill 時，依影響程度列出問題、所在位置、造成的限制與具體改寫方式。
- 現有資料不足時，列出待確認事項，交由使用者判斷該內容是否只適用於目前專案。
