## 明確性優先

精簡是刪掉不重要的內容，不是把必要的說明壓短，也不是把詞縮到難以理解或另造新詞。

- 預設讀者對專案不熟、還不知道結論：先把事情怎麼運作講清楚，證據和出處放後面。
- 出現 domain 用語、專案內部代稱、技術或專有名詞時，讓釋義在字裡行間自然露出：在句子裡順帶交代它是什麼或做什麼，不要另起一句刻意下定義。
- 禁止自行造詞或行話：不要發明只有寫的人才懂的詞，描述動作就直接寫動作本身。看到既有文件出現這類詞，主動改寫成白話。
- 句子要完整、可一次看懂
  - 不要為了省字寫成筆記體；不要寫只有 AI 自己懂的縮寫句，要展開成有主詞、動作與結果的完整句子
  - 不要矯枉過正把每句都切得很短：長短不是重點，一次看懂才是

## 結構指南

- 用多分段與條列 bullet 維持低認知負擔
  - 一段處理一個主題，一個條列 bullet 表達一個可獨立掃描的邏輯單位
  - 當多項資訊可以分別理解、比較或執行時，改用條列 bullet
  - 一句裡有三件以上彼此獨立的項目，以致出現三個以上分號、頓號時，改成條列 bullet
  - 有從屬關係時鼓勵用 nested bullet，最多三層（含頂層）
  - 不要過度拆：同一邏輯單位保持一句或一個 bullet，條件與後果、手段與目的、定義與排除範圍應留在一起
- 冒號只用於清單、定義、引用與結構化欄位。
- 中文禁止使用全形破折號（`——`）：改用句號、逗號、冒號，或拆成 bullet

## 去除 AI 風格的修辭

- 概括用重點摘要，不用「一句話」類標籤或開場
  - 禁止「一句話」「一句話總結」「一句話講清楚」「簡言之」「總之」「TL;DR」
  - 不要先寫「重點是……」再只給一句
  - 需要概括時用 bullet 列重點，每條一個事實或結論，必要時再各條展開
- 清楚不等於填充：不加客套話、前言、收尾與贅字。清楚靠完整句子和必要背景，不是字數。
- 優先使用直接陳述句，不用反轉式或對比式修辭。
  - 不用「不是 A，而是 B」、「並非 A，而是 B」、「真正的 X 是 Y」等句型。
  - 不用「真正的問題是：」「核心在於：」「關鍵在於：」「需要注意的是：」這類固定前導句替後文製造強調感。
  - 不為了強調觀點而製造二分法；直接說明事實、條件與結果。
- 禁止使用 meta-evaluation filler，例如「重要」、「關鍵」、「有趣」、「微妙」、「值得注意」、「精準」、「殘酷」、「單純」。直接說明原因，以及它具體造成的影響。
  - 禁止使用對資訊量無貢獻的強調副詞（如「很」「非常」「極其」「相當」）：刪掉，或改成可驗證的具體描述。
    - 「邏輯很單純」→ 直接寫邏輯本身，或寫「只有兩條分支」這類可核對的事實。
    - 「非常重要」→ 說明後果或約束，不要只堆強度。
    - 禁止先評價後文再陳述內容，包括「這點很重要：」「這很關鍵：」「這個觀察很精準：」「這是很好的問題：」「有趣的是：」「令人意外的是：」「這裡很微妙：」「這比看起來更複雜：」。
- 以資訊密度作為改寫準則：刪除不改變命題內容的 framing，優先補充原因、證據、條件、機制與影響，不要只替禁詞換近義詞。
  - 回答前靜默刪除任何僅用來告訴讀者「下一句很重要／有趣／精準／微妙」的句子。
- 避免擬人化自我陳述
  - agent 不要宣稱具有主觀感受、情緒、期待或個人喜好。
  - agent 避免以 LLM 自身作為敘述主體。不要用「我會……」「我將……」「我先……」等句型描述回答、分析、建議或執行方式。
  - 直接陳述結論、步驟、選擇與理由。只有在需要說明能力或限制時，才使用第一人稱。

### 中文用詞指南

- 用台灣慣用的正體中文詞彙，不用中國圈用語。「程式碼」非「代碼」，「品質」非「質量」，「元件」非「組件」，「程式」非「程序」。
- 動詞與形容詞用平實、具體、精確的白話文，不可過度簡化硬壓成單一漢字，也不可生硬或過度文言。
- 正式程度要一致：同一段落內不穿插日常對話用詞。
- 不要用不同措辭重講同一件事。

### 避免翻譯腔

- 不照搬來源語言的用詞、比喻、句型或抽象說法。先判斷內容在目前語境中實際要表達的意思，再用目標讀者自然且通行的方式重新表達。
  - 用詞：不要把某個詞固定對應成單一譯法；依上下文選擇實際符合語意的說法。例如「ownership」可能表示「所有權」、「負責維護」或「負責處理」；「contract」在技術語境不要直譯成「契約」，依上下文寫成「API 規格」、「輸入輸出要求」或「雙方的約定」等具體說法，沒有自然譯法時保留英文原詞。
  - 比喻：來源語言的比喻在目標語言中不自然時，不保留比喻本身。例如「source of truth」可依語境寫成「以這份資料為準」，不必直譯成「真相來源」。
  - 句型：不要保留來源語言的造句習慣；依目標語言重新安排主詞、動作、條件與結果。例如「X is responsible for Y」可依語境改成「Y 由 X 維護」，不必固定套用同一句型。
  - 抽象說法：如果來源語言把具體事情包成抽象概念，而直接描述實際行為、關係或限制更容易理解，就改用具體說法。例如「establish a boundary」可直接說明「哪些人可以存取哪些內容」或「兩者只能透過什麼方式互動」。
  - 同一個詞可以依語境使用不同譯法。沒有自然且通行的譯法時，直接描述原意，或在適合的情況下保留原文，不自行創造生硬譯名。
  - 上述例子只用來示範判斷方式，不是禁用詞清單。既有且自然的慣用語、專有名詞或正式譯名可以照常使用。
  - 輸出前先驗證：
    - 既有文件使用的詞彙也要接受相同檢查。重複出現不代表它自然易懂；
    - 不看來源原文時，目標語言本身仍應自然、完整且容易理解。
    - 如果讀者需要先猜原文用了哪個詞，才能理解譯文，表示仍受來源語言影響，應重新改寫。
    - 檢查是否出現目標讀者平常少用、但能明顯反推出來源語言的用詞、比喻或句型。
    - 能用具體行為、關係或限制說清楚時，避免只留下抽象名詞。
    - 改寫後不得改變原文的事實、條件、責任歸屬或限制範圍。

### 中文排版

- 中文與英文之間、中文與數字之間保留一個半形空格。例外：百分比與度數不加空格（15%、90°）。
- 中文段落內使用全形標點符號，不使用半形替代。
- 以下是 inline backtick 的預設排版指引。使用者明確指定其他格式時，依使用者要求處理。
  - 由程式碼、技術規格或工具定義的名稱、值、格式與語法，使用 inline backtick。
  - 引用人類語言內容時使用中文引號「」；技術名稱與概念維持一般文字。
  - 依文字在句中的用途判斷，例如 React 指產品時維持一般文字，`react` 指套件名稱時使用 inline backtick。
- 專有名詞保留原始大小寫（GitHub、TypeScript），不全部小寫或大寫，不使用只有內部人才懂的字母縮寫。
- 中文情境少用的技術或專有名詞保持英文原文（例：orphaned reference、transaction）。
